# Движок внутри приложения: сделано

До этого tsukiko требовал `brew install whisper-cpp` и запускал то, что
найдёт в PATH. Это чужая вещь, которую приложение не контролирует:
её версия неизвестна, её могут снести, и тогда расшифровка молча
перестаёт работать.

## Как поступают обычно

Три способа, и выбор между ними решает не вкус, а лицензия и размер.

**Просить установить самому.** Так живут обёртки над yt-dlp и ffmpeg.
Дёшево для автора, дорого для человека: скачать, распаковать, разрешить
запуск в настройках безопасности, повторить для каждой зависимости.

**Скачивать при первом запуске.** Так делают, когда лицензия запрещает
класть чужое внутрь своего (ffmpeg под LGPL) или когда груз слишком
велик. Работает это на тонкости: карантинную метку
`com.apple.quarantine` вешают браузеры и почтовые клиенты, а `curl` —
нет, поэтому скачанное программой Gatekeeper не проверяет. Тонкость
неприятная сразу с двух сторон: она же и дыра в защите, и опора,
которую Apple может убрать. Плюс на Apple Silicon любой бинарник обязан
иметь хоть какую-то подпись, иначе система убивает его на запуске, —
значит, за подпись скачанного надо отвечать самому.

**Класть внутрь приложения.** Так делают все, кому лицензия это
позволяет: бинарник лежит в `Contents/Helpers`, подписывается вместе
с приложением одной подписью, ничего не качает и работает без сети.

## Что выбрано и почему

Третье. whisper.cpp под MIT — класть внутрь можно, текст лицензии едет
рядом, в `Contents/Resources`. Груз оказался небольшим: два бинарника
на 14 МБ, приложение выросло с 47 до 59 МБ.

Всё остальное после этого решается само:

* **Скачивать нечего.** Значит, нет и вопроса «а если он уже есть
  в системе» — мы ничего не тянем ни при первом запуске, ни потом.
* **Удалять нечего.** Чужой whisper.cpp tsukiko не ставит, не правит
  и не удаляет: он просто ему не нужен.
* **Сломать снаружи нечем.** Снесённый Homebrew на приложение не влияет.
* **Версия своя и известная.** Это важнее, чем кажется: мы передаём
  модели флаги, которых в старых сборках нет вовсе — `--vad`, `-mc`,
  `--carry-initial-prompt`, `-ot`. На чужой сборке распознавание либо
  падает, либо молча работает хуже.

Системный движок остаётся запасным путём: своего нет — работаем на том,
что нашли в PATH. В инспекторе при этом честно написано, на чьём движке
идёт работа: «свой» или «из системы».

## Как собирается

`tool/engine.sh`: качает исходники закреплённой версии (v1.9.3), сверяет
архив по sha256, собирает через cmake и кладёт два бинарника
в `macos/Engine`. Собранное в репозиторий не попадает.

Сборка статическая (`BUILD_SHARED_LIBS=OFF`) и универсальная
(`arm64;x86_64` — как само приложение). Это и есть главное удобство:
готовые бинарники линкуются только с системными фреймворками, шейдеры
Metal вшиты внутрь. Ни библиотек рядом, ни правки путей загрузки
(`install_name_tool`), ни отдельной подписи для каждой `.dylib` —
ничего этого не нужно. Проверено `otool -L`: кроме Accelerate, Metal,
Foundation и libSystem, зависимостей нет.

Для сравнения, сборка из Homebrew так не умеет: она собрана с общими
библиотеками и подгружает бэкенды `.so` из своей папки в Cellar —
скопировать её внутрь приложения нельзя, она развалится.

`tool/sign.sh` кладёт собранное в `Contents/Helpers` и подписывает
изнутри наружу: сначала вложенное, потом сам бандл — иначе подпись
не собирается. `Contents/Helpers` — то место, куда macOS велит класть
вложенные программы, и по правилам подписи там не должно быть ничего,
кроме них, поэтому текст лицензии лежит в `Resources`.

Cmake нужен только тому, кто собирает приложение. Готовому приложению
не нужен никакой.

## Что из этого переезжает на Windows

Сам подход — целиком: движок кладётся рядом с программой при установке,
ничего не качается на месте. Место другое: у macOS это
`Contents/Helpers`, у Windows — папка `Engine` рядом с `.exe`. Знает
об этом только `os.engineDir`, остальному Dart всё равно.

### Ускоритель: Vulkan вместо CUDA — проверено

На macOS одна сборка покрывает все машины: Metal есть везде и вшивается
внутрь. У Windows выбор, и он оказался несложным.

| | что даёт | чего стоит |
|---|---|---|
| процессор | работает везде | медленно |
| CUDA | быстро, но только NVIDIA | **640 МБ** библиотек |
| Vulkan | быстро на NVIDIA, AMD и Intel | ничего сверх драйвера |

Числа не на глаз: официальные сборки whisper.cpp весят 8 МБ
процессорная и 640 МБ с CUDA 12.4 (257 МБ с CUDA 11.8) — это и есть
вес библиотек CUDA, которые пришлось бы возить с собой ради одного
производителя видеокарт.

Vulkan не возит ничего. Шейдеры компилируются в SPIR-V при сборке
и вшиваются в бинарник; на машине нужен только загрузчик
`vulkan-1.dll`, а его кладут драйверы — и NVIDIA, и AMD, и Intel.
Те ~200 МБ, которыми пугает Vulkan, — это его SDK, и он нужен **только
при сборке**: `find_package(Vulkan COMPONENTS glslc REQUIRED)` зовёт
компилятор шейдеров. В готовую программу из него не попадает ничего.

### Почему сборок всё-таки две

Проверено по исходникам ggml, а не по форумам.

**Нет видеокарты — не беда.** `ggml_backend_vk_reg()` оборачивает
поиск устройства в `try/catch` и при неудаче возвращает `nullptr`:
бэкенд просто не регистрируется, и та же самая Vulkan-сборка считает
на процессоре. Отдельная сборка ради этого не нужна.

**Нет `vulkan-1.dll` — беда.** `ggml_vk_instance_init()` зовёт
`vkGetInstanceProcAddr` напрямую, а cmake линкует `Vulkan::Vulkan`, то
есть импорт неявный. Windows убивает такой процесс на запуске, до
первой строки кода, — своей обработки ошибок движку не достанется.
Библиотеки нет там, где нет драйвера: чистая установка на базовом
видеоадаптере, виртуальные машины, серверные сборки.

Отсюда правило выбора (`os.engineNames`): есть загрузчик — берём
Vulkan-сборку, нет — процессорную. Копии под именем без суффикса
не делаем: она подменяла бы этот выбор и раздувала установщик.

### Остальные различия

Статичность достигается через `CMAKE_MSVC_RUNTIME_LIBRARY=MultiThreaded`
вместо вшитых шейдеров Metal, и vcredist не нужен. Подписывать вложенное
отдельно, как на macOS, не требуется: правила «изнутри наружу» у Windows
нет.

Больше беспокойства вызывает не whisper, а подготовка звука: на macOS
это системный `afconvert`, на Windows её нечем сделать без `ffmpeg` —
он под LGPL, и возить его внутри можно только с оговорками.
