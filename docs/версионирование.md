# Версии tsukiko

Систему версий ввели с **0.8.3+2**, до первого публичного стабильного выпуска.
Источник версии — `version:` в `pubspec.yaml`: формат `MAJOR.MINOR.PATCH+BUILD`.
Номер после `+` нужен для версии бинарного файла и пакета Flutter. Пользователю
показываются первые три числа.

## Когда менять числа

- `PATCH`: исправление ошибки без изменения ожидаемого поведения функций (`0.8.3` → `0.8.4`).
- `MINOR`: новая функция или заметное расширение существующей (`0.8.3` → `0.9.0`).
- `MAJOR`: несовместимая переработка или первый стабильный публичный выпуск (`0.x.y` → `1.0.0`).
- `BUILD`: увеличивать на 1 при **каждой новой версии для сборки**. Для Windows и macOS одного выпуска число одинаково. После начальной `+2` у следующей версии будет как минимум `+3`.

Версию повышают **перед официальной сборкой**, а не при каждом рабочем коммите.
Обычные коммиты могут оставаться на той же версии. Каждая новая опубликованная
сборка для одной платформы обязана иметь новую тройку `MAJOR.MINOR.PATCH` и
больший `BUILD`, чем у предыдущей сборки этой платформы. Одну версию можно
собрать один раз для Windows и один раз для macOS — это один выпуск.
Повторная попытка после неудачной сборки допустима: версия резервируется лишь
после успешной загрузки артефактов.

## Порядок выпуска

1. Изменить `version:` в `pubspec.yaml`, `appVersion` в `lib/platform/os.dart`
   и резервные значения в `windows/runner/Runner.rc`.
2. Запустить `python3 tool/version.py check`. На Windows подходит `python`.
3. Коммит с `[build-windows]`, `[build-macos]` или `[build]` запускает нужную
   сборку **только при push в main**. `[release]` равнозначен `[build]`.
   macOS-сборка на GitHub требует настроенного сертификата в Secrets;
   отсутствие сертификата теперь останавливает сборку до публикации.
4. Перед затратной частью CI выполняет `tool/version.py build --platform ...`:
   он сравнивает версию с уже собранными выпусками на GitHub. Если номер
   повторился или уменьшился, сборка останавливается.
5. После успешной загрузки артефактов CI создаёт служебный тег
   `build/windows/vX.Y.Z+N` или `build/macos/vX.Y.Z+N`. Он фиксирует, что
   эта версия уже собрана. Эти теги не удалять и не переназначать.
6. Для публичного выпуска создать обычный тег `vX.Y.Z` и GitHub Release,
   приложив артефакты. Тег выпуска сам по себе повторную сборку не запускает.

Установщик Windows получает `X.Y.Z` и `N` из `pubspec.yaml`; прямой запуск
Inno Setup без этих значений запрещён. macOS берёт версию из Flutter.
Локальный `tool/package-win.ps1` также проверяет служебные теги перед сборкой.
Одна команда `flutter build` годится для разработки, но не является процедурой
выпуска: Windows-дистрибутив создаёт CI, macOS — CI с сертификатом или
описанная ниже локальная сборка с постоянной подписью. После успешного
выпуска версия резервируется служебным тегом.

### Подписанная macOS-сборка на рабочем Mac

Пока сертификат Apple Development хранится только в локальной связке ключей,
macOS собираем на этом Mac. Закрытый ключ в GitHub не передаём:

```sh
python3 tool/version.py check
python3 tool/version.py build --platform macos
flutter pub get
flutter build macos --release
TSUKIKO_EXPECTED_TEAM=YOUR_TEAM_ID ./tool/sign.sh
./tool/dmg.sh
```

`tool/sign.sh` отказывается выпускать сборку без постоянной подписи. Режим
`TSUKIKO_ADHOC_SIGN=1` допускается только для локальной разработки, не для
выпуска: после обновления macOS считает её другим приложением для разрешения
«Универсальный доступ», и глобальные хоткеи перестают работать. После проверки
DMG сохранить артефакт, затем создать и отправить служебный тег
`build/macos/vX.Y.Z+N`, чтобы повторная версия не прошла контроль.
