# Как устроен tsukiko

Карта для того, кто будет портировать приложение на другую систему или
разбираться в нём заново. Разговор о слоях, не о функциях: что от чего
зависит и где проходят границы.

## Три движка в одном процессе

Приложение — один процесс, в котором работают три движка Flutter, у каждого
свой изолят и своё окно.

| Движок | Точка входа | Что рисует | Когда создаётся |
|---|---|---|---|
| главное окно | `main()` | очередь, расшифровка, инспектор | при запуске |
| панель | `panelMain()` → `runPanel()` | поповер у строки меню, вся диктовка | при запуске, живёт всегда |
| настройки | `settingsMain()` → `runSettings()` | окно настроек | при первом ⌘, |

Так вышло не от хорошей жизни: движок отдаёт свой вид одному окну. Зато
диктовка не зависит от того, открыто ли главное окно, — она в своём изоляте
и работает со спрятанной панелью.

Изоляты не видят память друг друга. Общаются они двумя способами:

- **через файл настроек** — с очередью записи (см. ниже);
- **через родную сторону** — одно окно правит настройки, зовёт
  `settingsChanged`, Swift рассылает `reload` всем остальным каналам.

## Границы

Две штуки, и путать их не надо.

### `lib/os.dart` — граница операционной системы

Всё, что **в самом Dart** делается по-разному: где лежат файлы, как найти
чужой процесс, чем переложить звук в WAV, как показать файл в проводнике,
как назвать модификатор клавиши.

```
os.dart          договор (abstract class Os) + выбор реализации
os_macos.dart    macOS: ps, pgrep, lsof, afconvert, open, ~/Library
os_windows.dart  Windows: tasklist, taskkill, ffmpeg, explorer, %APPDATA%
```

Порт на Windows сделан:

| macOS | Windows |
|---|---|
| `pgrep -f` / `ps -axo` | `tasklist` / WMI |
| `lsof -t` | `handle.exe` или пропустить (признак необязательный) |
| `footprint -p` | `GetProcessMemoryInfo` |
| `afconvert` | `ffmpeg` |
| `open -R` | `explorer /select,` |
| `~/Library/Application Support/<id>` | `%APPDATA%\<id>` |
| `SIGTERM`/`SIGKILL` | `TerminateProcess` / `taskkill` |
| `⌘`, `⌥`, `⇧` | `Ctrl`, `Alt`, `Shift` |

Проверить, что граница не протекла:

```sh
grep -rn "Process\.run\|Platform.environment\|split('/')" lib/ | grep -v os_macos | grep -v os_windows
```

Пусто — значит остальной Dart о системе не знает. Единственные исключения:
`Process.start` для найденного через `os.findExecutable` whisper (это уже
портируемо) и `lib/legacy_migration.dart` (разовый переезд, подлежит
удалению).

### `lib/bridge.dart` — граница родного кода

Перехват клавиш, микрофон, вставка текста, окна, значок в строке меню,
Корзина, автозапуск. Здесь **платформы нет вовсе**: файл целиком — один
`MethodChannel`, и на любой системе он одинаков. Разница живёт на той
стороне канала.

```
bridge.dart              Dart-сторона канала, портируемая как есть
macos/Runner/*.swift     macOS-сторона (Dictation.swift, TrayPanel.swift и др.)
windows/runner/*.cpp     Windows-сторона (dictation_bridge.cpp, flutter_window.cpp)
```

Что должна уметь родная сторона, видно по `switch (call.method)`
в `Dictation.swift` и по вызовам `_channel.invokeMethod` в `bridge.dart`.
Обратные события: `hotkey`, `captured`, `panelShown`, `panelHidden`, `hud`,
`reload`, `tab`, `yieldModel`.

Раньше здесь стояли четыре абстрактных класса (`HotkeyBackend`,
`AudioRecorder`, `TextInserter`, `PanelPresenter`) с одной реализацией и
ни одним местом, где они использовались бы как типы. Удалены: вторая
реализация в Dart не нужна, нужен второй `runner` на C++.

## Раскладка

По фичам, а не по слоям. Папки `blocs/`, `cubits/`, `widgets/` разложили бы
код по одному признаку и сломались на первой правке: чтобы поменять одну
вещь в диктовке, пришлось бы обойти пять папок. Фичи же лежат на том, что
в этом коде есть физически, — три движка, три экрана.

```
lib/
  main.dart                  только три точки входа

  platform/                  границы
    os.dart  os_macos.dart   что по-разному делается в самом Dart
    bridge.dart              канал к родному коду

  core/                      предметная область, ни строчки про UI
    text.dart                склонения, длительности, названия языков
    library.dart             пути, раскладка по месяцам, свободные имена
    models.dart              каталог, поиск, проверка, имена, загрузка
    whisper.dart             RunOptions и аргументы whisper-cli
    whisper_server.dart      сервер, метки, уборка сирот, сочетания клавиш
    transcript.dart          сегменты, парсеры, рендеры, форматы
    settings.dart            хранение настроек

  l10n/                      app_ru.arb, app_en.arb и то, что из них
                             генерируется (gen/, в git не хранится)

  features/
    dictation/               кубит, состояние, поповер,
                             dictation_repository.dart — единственная
                             дорога, по которой очередь узнаёт про диктовку
    queue/                   блок, события, состояние, окно, widgets/
    settings/                окно настроек

  design/                    токены, общие элементы, кот

  legacy_migration.dart      временный, удаляется целиком
```

Внутри каждой фичи то, что написано на `macos_ui`, — это ровно то, что
Windows-версия заменит; остальное переезжает как есть. Граница видна
прямо в дереве папок. `test/` повторяет ту же раскладку.

## Состояние

Взят пакет `bloc`. Состояние всего приложения живёт в трёх владельцах,
по одному на движок:

| Движок | Владелец | Почему так |
|---|---|---|
| главное окно | `QueueBloc` | полный Bloc: события нужны по делу |
| панель | `DictationCubit` | действия прямые, отбрасывать нечего |
| окно настроек | `SettingsCubit` | «поставить галку» и «выбрать значение» |

По умолчанию **Cubit**: взаимодействия прямые — нажали клавишу, значит
начать запись, — и заводить под каждое действие класс события было бы
церемонией без выгоды.

В виджетах остаётся только то, что к предметной области не относится:
наведение курсора, нажатие, перетаскивание, открытая панель поиска и
строка запроса. Там `setState` уместен, и трогать его незачем.

**Полный Bloc — у очереди распознавания**, где события нужны по делу:
`droppable()` отбрасывает «Распознать» при уже идущей очереди (раньше это
была проверка `if (_running) return` внутри обработчика), а по журналу
событий видно, что происходило перед сбоем.

`GetX` не рассматривался всерьёз: роутинга здесь нет вовсе (три движка,
у каждого одно окно), а остаётся глобальный сервис-локатор — ровно то,
от чего этот код уходит.

**Состояние неизменяемо и состоит из значений.** Это не формальность:
Cubit решает, перерисовывать ли, сравнением снимков, а сравнивать
изменяемые объекты бессмысленно — у `DictationSettings` и `Download`
содержимое меняется без замены самого объекта, и панель молча замирала бы
на устаревшем виде. Поэтому в `DictationState` лежат уже разобранные
подписи сочетаний и готовая строка хода загрузки, а не сами объекты.

**Службы в состояние не входят.** `WhisperServer`, `NativeBridge`, таймеры,
работающий `Process` — поля кубита или блока. Сервер подставляется через
конструктор: настоящий поднимает процесс и читает в память полтора
гигабайта, а тестам это ни к чему.

**Диалогов в блоке нет.** Он не знает, что такое окно. Когда нужен ответ
человека — «модель занята, продолжить?» — блок кладёт вопрос в состояние
(`QueueState.ask`), окно его показывает, а ответ возвращается событием
(`RunConfirmed`). Так же устроены выбор файла и «Сохранить как…»: диалог
открывает окно, а блоку приходит уже готовый путь.

**`Job` неизменяем.** Правка на месте сравнению состояний невидима, и
очередь замирала бы на устаревшем виде. В сравнение входит длина списка
живых фрагментов, а не сами фрагменты: список только растёт, а сверять
тысячи сегментов на каждой перерисовке незачем.

Мелочь, которая кусается: службы отвечают когда угодно и могут ответить
уже после `close()`. Все `emit` идут через `_emit`, который молчит на
закрытом кубите. В приложении кубит не закрывается никогда, но в тестах —
на каждом шаге.

Нижние два слоя от Flutter почти не зависят и переезжают как есть.
Верхний написан на `macos_ui` — для Windows его придётся переписать
(`fluent_ui` или свой), и это ожидаемо: родной вид системы не портируют.

## Хранение

| Файл | Кто пишет | Что |
|---|---|---|
| `settings.json` | главное окно и окно настроек | всё общее |
| `dictation.json` | окно настроек | сочетания, модель и подсказка диктовки |
| `whisper-server.pid` | панель | pid живого сервера |

Обе записи атомарны: во временный файл рядом и переименованием на место.
`rename` на одной файловой системе неделим, поэтому читатель видит либо
старый файл целиком, либо новый — но никогда половину.

`settings.json` правят три изолята, и «прочитать → слить → записать» между
ними надо выстроить в очередь. Файловый замок для этого не годится:
POSIX-замки принадлежат процессу, а изоляты живут в одном процессе — второй
проходит сквозь замок первого (проверено). Поэтому пишет всегда один изолят:
кто первым занял имя в `IsolateNameServer`, тот и владеет файлом, остальные
шлют ему правки портом. Читают все напрямую.

## Модель в памяти

Самая дорогая вещь в приложении — файл модели на полтора гигабайта.
Отсюда три механизма, которые иначе выглядят избыточными:

1. **Один сервер на диктовку.** `whisper-server` держит модель между
   фразами: холодный запуск стоит секунд, горячий — полсекунды.
2. **Подбор сирот.** Сервер переживает падение приложения. Ищем по метке
   в аргументах процесса, а не по pid-файлу: файла может не быть вовсе.
   Метки — единственный источник, `ourServerMarks`; родная сторона получает
   их через `setServerMarks`, своей копии не держит.
3. **Уступка.** Очередь и диктовка не поднимают две модели разом. Очередь
   спрашивает разрешения (`requestModel`), диктовка отвечает; за чужими
   приложениями следит `modelUsage` — по процессорному времени, росту
   памяти и открытым дескрипторам.

## Что осталось несделанным

- **Управление моделями** — см. `задача-управление-моделями.md`. Делать
  после очереди: единый список моделей это ровно то состояние, у которого
  сейчас нет хозяина.
- **Интерфейс без локализации.** Строки — русские литералы в коде.
  Платформозависимое из них уже вынесено (`os.fileManagerName`,
  `os.shortcutLabel`), остальное ждёт `intl`.
